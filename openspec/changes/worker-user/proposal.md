## Decisions

1. **The worker runs as a separate Unix user** (Adam, 2026-10-11). *Rejected:* Claude Code's
   sandbox, whose read limits on a process an allowed command starts are unmeasured and belong to
   whichever release is installed; and keeping the App's key off the host, which bounds a leak
   but stops none.
2. **`sudo` starts the worker, under one sudoers line per worker user:
   `igor ALL=(igor-worker-<role>-<rank>) NOPASSWD: ALL`** (Adam, 2026-10-11, with one worker user
   per instance from decision 7). Each line lets the service user act as that worker user and nobody
   else. *Rejected:* a setuid helper, which is security-critical code Igor would ship; and
   `systemd-run --uid=`, which exposes a unit's environment, seat token included, to every local
   user over D-Bus.
3. **`igor serve` always runs its worker as its worker user, and `igor run` always runs it as
   the Igor's own user, with a notice** (Adam, 2026-10-11; amended 2026-10-17). `serve` refuses
   to start if its worker user does not exist, and has no `--same-user` flag. `run` is the
   one-shot command for development. So `serve` means a worker user and `run` means none, and
   nothing else tells the Igor which. macOS runs `serve` only in #192's container image
   (`deploy-image`), and on macOS itself runs `run`. *Rejected:* `serve --same-user`, an
   unattended Igor whose worker can read its credentials; refusing both without a worker user,
   which adds a step to every development run; and warning in both, where one forgotten setting
   on a server would bring back the exposure #163 found.
4. **`igor doctor` (#113) gets no check** (Adam, 2026-10-11). Only the Igor process knows its key
   paths and pid, so the Igor checks isolation when it starts. Under decision 3 only `serve`
   has a worker user, so only `serve` checks.
5. **Instance names use a dash, `igor@<role>-<rank>`, with the rank always written. The unit
   passes `%i`, the instance name such as `reviewer-2`, to `igor serve`, and the Igor sudoes to
   `igor-worker-` followed by that name** (Adam, 2026-10-17, including how the Igor
   learns the name). The name is plain concatenation: forming it does not parse the instance name
   into a role and a rank, whatever #179 does with the name for its own purposes. A sibling
   rank that sweeps a gone rank's trees (decision 19) builds that rank's worker user the same
   way, from the role and the gone rank's number, as #179's roster and sweep identify it. The
   unit's `User=` and `Group=` stay the service user, because they set the account the Igor
   itself runs as. `SupplementaryGroups=igor-worker-%i` puts the Igor in the worker's group,
   and `ReadWritePaths=/var/lib/igor-worker-%i` keeps the worker's home writable. No drop-in
   is generated per instance, and no step edits `/etc/group`. The GitHub App identity stays
   one per role; the rank appears only in names on the host, such as the unit, the worker user
   and its group, never in a GitHub identity. This change depends on #179
   (`concurrent-instances`) naming instances `<role>-<rank>`, which #179 is to do in its own
   next revision. *Rejected:* a key in `igor.config.yaml`, which a lore pull request could
   point at the service user; setting `User=` and `Group=` to the worker user, which would run
   the Igor itself as the worker; an environment variable such as `IGOR_WORKER_USER`, which
   would be a second source for the name the argument already gives; a unit drop-in generated per instance;
   and naming the user `igor-worker-<role>.<rank>`, since a dot in a user name reads as
   `user.group` to tools such as `chown`.
6. **A changed file the Igor cannot read stops the run**, rather than being left out of the
   artifact. While the worker chooses which files are unreadable, skipping them is not safe.
7. **One worker user per Igor instance, `igor-worker-<role>-<rank>`** (Adam, 2026-10-17). The
   name is `igor-worker-` followed by the instance name `<role>-<rank>` (decision 5). Each
   instance has its own home
   and its own sudoers line, generated by the deployment templates. *Rejected:* one worker user
   shared by every role on a host, and one per role. On Linux, processes of one user can normally
   read each other's `/proc/<pid>/environ`, so a worker could read the seat token of another
   role, or of another rank of its own role drawing on a different seat. A shared home is a second
   route: one worker can leave a file, such as `~/.npmrc`, that another then runs. Task 6.6 still
   measures the `/proc` reach between two units, and its result goes into the docs; building the
   per-instance users does not wait for it.
8. **`deploy/igor.service` drops `NoNewPrivileges`**, which stops `sudo` from changing user, and
   **`claude` moves to `/usr/local/bin`**, because the worker cannot enter the service user's
   home.
9. **A changed symbolic link is published as a link once #137 lands** (Adam, 2026-10-17). #137
   (`carry-what-a-tree-holds`) is an open change that publishes a link as its target text, mode
   `120000`. The Igor reads the link with `lstat` and `readlink` and never follows it, so the
   file it points to never reaches the artifact. Until #137 lands, a changed link stops the
   run, because the publishing paths can carry only regular files.
10. **Every `claude -p` that runs in the worker's tree runs as the worker user, and the Igor
    reads the tree only after the last of them exits** (Adam, 2026-10-17). The model steps
    include #153's (`signed-publishing`) prose pass and bug hunt after the worker, which run
    repository code such as `npm test` and edit the tree. The link checks and the Igor's read
    come after the last of them.
11. **`skills_dir` (#174) joins the start check's write probe** (Adam, 2026-10-17). As the worker
    user, the check tries once to create and delete a file there, and refuses to start if it
    can. The worker never needs to write there.
12. **#153's steps are signed once, at the end, by the Igor** (Adam, 2026-10-17, including
    who signs). Bug-hunter runs, then the prose pass. Each edits the tree as it needs and ends
    by reporting its pass result: bug-hunter its result block, and the prose pass the pass token
    from its first `prose check` call. Then bug-hunter's triage
    runs on the prose pass's diff: a diff that touches only comments or docs is skipped, and
    anything else gets one more bug-hunter iteration. After the last model step exits, the Igor
    stages the changed paths once, in its own index, which the worker cannot write. It then runs
    both signing calls itself, as the service user: the second `prose check` call, with the prose
    pass's token, and bug-hunter's minting script, against the staged tree. So each trailer that
    binds a tree, `Prose:` and #153's `Bug-hunter-Tree:`, names the tree the Igor records and
    publishes (decision 17), or the tree #153 binds to instead where its task 0.4 finds the Git
    Data API's tree differs,
    never the worker's index copy or any other copy the worker could change. The signing
    scripts come from the root-owned skills directory, `skills_dir` (decision 11), so running
    them as the service user runs nothing the worker wrote.
    *Rejected:* the Igor staging before each signing step, which would run `git add` over
    the worker's files before the link checks, and leave the prose pass's edits out of the tree
    bug-hunter's trailer is bound to; and the steps signing for themselves, which they cannot
    do as a user that cannot write the Igor's index.
13. **A changed submodule pointer is published as a pointer once #137 lands** (Adam,
    2026-10-17). A changed gitlink, mode `160000`, is published as the commit it names, the way
    #137 publishes one, and the Igor never enters the submodule. Until #137 lands it stops the
    run, as a link does. A nested repository with working content in it still stops the run.
14. **The worker user's home lasts across runs, and only `~/.claude` and `~/.claude.json` are
    reset before each `claude -p`, from a template built into Igor, keeping
    `~/.claude/.credentials.json`, the stored Claude login** (Adam, 2026-10-17). #174
    (`pinned-skills`) owns three rules this change relies on: the reset (#174's decision 9); the
    kill of every process the worker user owns before every reset (decision 13); and the
    rewording of the in-force scenario *No state carries between tasks* to name what the home
    keeps (decision 15). So `~/.gitconfig` with its `safe.directory` setting, #153's session mark
    and tool caches stay, and a file one run leaves elsewhere in the home, such as `~/.npmrc`,
    reaches later runs of the same instance only.
15. **#153's `prose start` runs as the worker user, after #174's reset** (Adam, 2026-10-17),
    through the same `sudo` spawn. `prose start` writes #153's session mark, the file its prose
    steps check for before their first file write. Those steps run as the worker and look in the worker's
    home, so the mark must belong to the worker and sit there. The service user's
    `~/.local/state`, which the unit's `ProtectHome=read-only` makes read-only, is then not
    needed.
16. **Hard links are refused twice** (Adam, 2026-10-17). At startup, the Igor checks that
    `fs.protected_hardlinks` is `1` and refuses to start otherwise; with it, the worker cannot
    make a hard link to a file it cannot read, such as the App's key. And the Igor refuses to
    publish any changed file whose link count is above 1, so a hard link that exists anyway
    stops the run. A hard link to the key is a regular file inside the tree, not a symbolic link,
    so the Igor's symbolic-link checks (decision 9; design, *The Igor reads changes without
    following links*) do not catch one.

17. **The Igor publishes the tree it recorded before #189's checks, and discards what the
    checks write** (Adam, 2026-10-17). The Igor records the tree the model steps left, as a tree
    object in its own git directory, then runs
    #189's (`loop-verifies-commands`) checks, which run the role's commands, such as its tests,
    as the worker user, and publishes the recorded tree. #189's rule that checks do not change
    what is published stands.
18. **Every file the Igor reads from the worker's tree or outbox is opened without following a
    link, and read only if it is a regular file with one hard link** (Adam, 2026-10-17). That
    includes the declaration file, `reverts.json` in the outbox, where the worker states what
    its change discards. An error parsing a file read from the worker never quotes the file's
    content, so a declaration hard-linked to a key cannot carry the key's text into a refusal or
    a record.
19. **Worker trees live in the shared state directory, `/var/lib/igor/trees`, not in the
    instance's private `/tmp`** (Adam, 2026-10-17). #179 (`concurrent-instances`) needs a sibling
    rank to sweep a gone rank's trees after a crash, which it cannot do in another unit's private
    `/tmp`. The unit keeps `PrivateTmp=true` for everything else. The worker-group permissions
    apply under `/var/lib/igor/trees` as they did in `/tmp`: the tree `2770`, the outbox `2770`,
    and `<tree>-git` read-only to the worker. #179's task 4.20 left open whether trees stay in
    each instance's private `/tmp`, as this change had them, or move to the shared state
    directory, for whichever of #179 and this change lands second to settle; this settles it.
20. **The implementation of this change adds the worker users and `sudo` to #192's container
    image** (Adam, 2026-10-17). #192 (`deploy-image`) merges as it is. This change's tasks,
    built at gate two, after this specification is approved, then add, to the
    image and the compose file: `sudo`, a worker user for each instance the compose file runs,
    their sudoers lines, and the trees volume at `/var/lib/igor/trees`. That image is how a Mac
    runs `serve` (decision 3).

## Why

A worker can read any file the Igor's service user can read
([#163](https://github.com/adamstallard/igor/issues/163)). Claude Code refuses its own Read tool
and `head` outside the tree, but a test file the worker writes in the tree runs under an allowed
`npm test` and reads whatever it likes. Measured on 2026-10-07, it printed a canary placed outside
the tree. The same route reads the per-role env file, the App's private key (#156), the seat
tokens, the age private key that decrypts seat files once #171 lands, and, on Linux, the Igor's
own `/proc/<pid>/environ`.

A worker takes instructions from issue text, which anyone who can file an issue can write. With
the App's key they can mint installation tokens for every repository the App is installed on,
until the key is rotated. Of the directions in the issue, a separate Unix user is the only one
that doesn't depend on Claude Code enforcing anything.

## What Changes

- **Under `igor serve`, the worker runs as a second Unix user**, `igor-worker-<role>-<rank>`,
  one per Igor instance. The Igor starts it through `sudo`, under a sudoers rule that lets the service user run commands as that
  one user and nobody else. The seat token reaches `claude` through its environment, never its
  arguments. Every later model step in the tree, such as #153's prose pass and bug hunt, runs as
  the same user.
- **The worker gets its tree, its outbox, its seat token and its tools, and nothing else.** The
  tree and outbox are shared through the worker's group, of which the Igor is a member. The
  git directory sits beside the tree, the Igor's and read-only to the worker. `git rm` and
  `git mv` write an index copy kept in the outbox, and the Igor reads the changes against its
  own index, never that copy.
- **Nothing the worker writes is run or followed by the Igor.** The Igor runs git in a tree
  with hooks, fsmonitor and submodule recursion off, and follows no symbolic link. It stops a
  run on a nested repository, a path beneath a link, or a file it cannot read, rather than
  dropping it. A changed link is published as a link once #137 lands, and stops the run until
  then, and a changed file with more than one hard link stops the run. Every file the Igor
  reads from the tree or the outbox, the declaration file included, is read only if it is a
  regular file with one hard link. These checks, and the Igor's read of the tree, come after
  the last model step in the tree exits. The Igor stages and records that tree, makes #153's
  trailers against it with the signing scripts from `skills_dir`, runs #189's checks, and
  publishes the recorded tree.
- **A kill, a release and the startup sweep act as the worker user** where the worker's own
  processes and files need it. Trees live under the shared `/var/lib/igor/trees`, so a sibling
  rank can sweep a crashed rank's trees (#179).
- **Every start of `serve` checks the isolation.** `serve` refuses to start, naming what is
  wrong, if the worker user is missing, privileged, or the Igor's own user, if `sudo` asks for a
  password, if the worker cannot run `claude`, or if the worker can read the Igor's process
  environment, a key or token file the Igor's configuration names, or a canary, or can write
  the lore checkout, the Igor's installation or `skills_dir`, or if `fs.protected_hardlinks` is
  not `1`. The env files systemd loads are not probed,
  since the Igor never learns their paths; the process-environment check covers what they hold.
- **`serve` always has a worker user, and `run` never does.** `run` runs the worker as the same
  user with a notice.
- **Deployment:** `deploy/igor.service` keeps `User=` and `Group=` as the service user, passes
  `%i` to `igor serve`, names the worker user `igor-worker-%i` for the worker's group and
  home, and drops `NoNewPrivileges`, which blocks `sudo`. A new `deploy/sudoers.example` and a
  section in `docs/deployment.md` cover creating a worker user, its home and its sudoers line
  for each instance. #192's container image gains `sudo`, the worker users and their sudoers
  lines, and its compose file mounts the trees volume at `/var/lib/igor/trees`. `claude` moves
  out of the service user's home, because the worker must be able to run it.

Not changed: triage and usage reads still run `claude` as the Igor, because triage allows no
tools and a usage read, the `claude` call that reads a seat's
quota, runs no item text.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `task-execution`: eight requirements added. The worker, and every model step in its tree,
  runs as a separate user. That user can write nothing the Igor depends on, and
  the Igor runs nothing it writes. The Igor reads no file through a link, and publishes the tree
  it recorded before #189's checks. The Igor makes #153's trailers itself, once, against the
  tree it staged after the last model step. A kill and a release reach what the worker owns. The
  isolation is checked before any work. And `serve` always has a worker user, while `run` never
  does. One is modified: *The worker is given an explicit environment holding no
  credential but its seat's* also passes `GIT_INDEX_FILE`, naming the worker's index copy.

## Decisions

1. **The worker runs as a separate Unix user** (Adam, 2026-10-11). *Rejected:* Claude Code's
   sandbox, whose read limits on a process an allowed command starts are unmeasured and belong to
   whichever release is installed; and keeping the App's key off the host, which bounds a leak
   but stops none.
2. **`sudo` starts the worker, under one sudoers line per worker user:
   `igor ALL=(igor-worker-<role>-<rank>) NOPASSWD: ALL`** (Adam, 2026-10-11, with one worker user
   per instance from decision 7). Each line lets the service user act as that worker user and nobody
   else. *Rejected:* a setuid helper, which is security-critical code Igor would ship; and
   `systemd-run --uid=`, which exposes a unit's environment, seat token included, to every local
   user over D-Bus.
3. **`igor serve` always runs its worker as its worker user, and `igor run` always runs it as
   the Igor's own user, with a notice** (Adam, 2026-10-11; amended 2026-10-17). `serve` refuses
   to start if its worker user does not exist, and has no `--same-user` flag. `run` is the
   one-shot command for development. So `serve` means a worker user and `run` means none, and
   nothing else tells the Igor which. macOS runs `serve` only in #192's container image
   (`deploy-image`), and on macOS itself runs `run`. *Rejected:* `serve --same-user`, an
   unattended Igor whose worker can read its credentials; refusing both without a worker user,
   which adds a step to every development run; and warning in both, under which a server whose
   worker user was never created would run its worker as the service user, the exposure #163 found.
4. **`igor doctor` (#113) gets no check** (Adam, 2026-10-11). Only the Igor process knows its key
   paths and pid, so the Igor checks isolation when it starts. Under decision 3 only `serve`
   has a worker user, so only `serve` checks.
5. **Instance names use a dash, `igor@<role>-<rank>`, with the rank always written. The unit
   passes `%i`, the instance name such as `reviewer-2`, to `igor serve`, and the Igor sudoes to
   `igor-worker-` followed by that name** (Adam, 2026-10-17, including how the Igor
   learns the name). The name is plain concatenation: forming it does not parse the instance name
   into a role and a rank, whatever #179 does with the name for its own purposes. A sibling
   rank that sweeps a gone rank's trees (decision 19) builds that rank's worker user the same
   way, from the role and the gone rank's number, as #179's roster and sweep identify it. The
   unit's `User=` and `Group=` stay the service user, because they set the account the Igor
   itself runs as. `SupplementaryGroups=igor-worker-%i` puts the Igor in the worker's group,
   and `ReadWritePaths=/var/lib/igor-worker-%i` keeps the worker's home writable. No drop-in
   is generated per instance, and no step edits `/etc/group`. The GitHub App identity stays
   one per role; the rank appears only in names on the host, such as the unit, the worker user
   and its group, never in a GitHub identity. #179 (`concurrent-instances`) names instances
   this way, in its requirement *A process is named by its role and rank*. That requirement
   also refuses, at load, a role name outside `[a-z][a-z0-9-]*`, and a role whose
   `igor-worker-<role>-<rank>` would pass Linux's 32-character limit on user names for any rank
   the roster declares for it (Adam, 2026-10-18), so every instance's worker user can be
   created. *Rejected:* a key in `igor.config.yaml`, which a lore pull request could
   point at the service user; setting `User=` and `Group=` to the worker user, which would run
   the Igor itself as the worker; an environment variable such as `IGOR_WORKER_USER`, which
   would be a second source for the name the argument already gives; a unit drop-in generated per instance;
   and naming the user `igor-worker-<role>.<rank>`, since a dot in a user name reads as
   `user.group` to tools such as `chown`.
6. **A changed file the Igor cannot read stops the run**, rather than being left out of the
   artifact. The worker chooses which files the Igor cannot read, so skipping them is not safe.
   #120 (`rename-arrives-whole`) states that rule, as *A path execution cannot read is never
   silently omitted*, and this change cites it rather than stating it again.
7. **One worker user per Igor instance, `igor-worker-<role>-<rank>`** (Adam, 2026-10-17). The
   name is `igor-worker-` followed by the instance name `<role>-<rank>` (decision 5). Each
   instance has its own home
   and its own sudoers line, generated by the deployment templates. *Rejected:* one worker user
   shared by every role on a host, and one per role. On Linux, processes of one user can normally
   read each other's `/proc/<pid>/environ`, so a worker could read the seat token of another
   role, or of another rank of its own role drawing on a different seat. A shared home is a second
   route: one worker can leave a file, such as `~/.npmrc`, that another then runs. Measurement
   6.6 (2026-10-18) confirmed the `/proc` route across two units: with one worker user shared,
   one worker read the other's seat token and wrote into its tree; with a user per instance,
   every attempt was refused.
8. **`deploy/igor.service` drops `NoNewPrivileges`**, which stops `sudo` from changing user
   (measurement 6.2: with it set, sudo refused to run), and **`claude` moves to
   `/usr/local/bin`**, because the worker cannot enter the service user's home (proposed
   2026-10-17; approved by Adam, 2026-10-19). Without `NoNewPrivileges` the worker can also run
   setuid programs, as any unprivileged account on the host can; it has no sudoers line, so none
   of them grants it more than they grant every other account.
9. **A changed symbolic link is published as a link once #137 lands** (Adam, 2026-10-17). #137
   (`carry-what-a-tree-holds`) is an open change that publishes a link as its target text, mode
   `120000`. The Igor reads the link with `lstat` and `readlink` and never follows it, so the
   file it points to never reaches the artifact. Until #137 lands, a changed link stops the
   run, because the publishing paths can carry only regular files.
10. **Every `claude -p` that runs in the worker's tree runs as the worker user, and the Igor
    reads the tree only while none of them runs** (Adam, 2026-10-17; reads between them allowed
    on 2026-10-19, decision 32), and after it has killed every process the worker user owns
    (decision 27). The model steps include #153's
    (`signed-publishing`) prose pass and bug hunt after the worker, which run repository code
    such as `npm test` and edit the tree. The link checks and every read and staging come after
    the steps started so far have exited.
11. **`skills_dir` (#174) joins the start check's write probe** (Adam, 2026-10-17). As the worker
    user, the check tries once to create and delete a file there, and refuses to start if it
    can. The worker never needs to write there.
12. **#153's steps run no signing script; the Igor runs every prose and bug-hunter signing call
    itself, as the service user** (Adam, 2026-10-17, including who signs; on 2026-10-18 Adam
    decided that the Igor also runs prose's first call, #153's decision 16). The order:
    1. Bug-hunter runs, edits the tree, and ends by reporting its `Bug-hunter:` value. It does
       not run its `caller-result.sh`, which as the worker user mints the wrong tree or none
       (#153's measurement 0.14).
    2. The Igor runs prose's first call, which prints the rules and a pass token, and gives both
       to the prose pass in its prompt. The prose pass edits the tree and writes the message by
       those rules.
    3. Bug-hunter's own triage, on the model #153 pins, runs on the prose pass's diff. A diff it
       skips gets no further iteration; any other gets one more bug-hunter iteration. That
       triage skips more than comments and docs, such as tests and specs (#153's measurement
       0.11), and #153 says whether that is the line it wants. No prose pass follows the extra
       iteration (Adam, 2026-10-18, on #153). #153 has a fresh model step read the commit's prose
       cold before prose signs, and the prose pass answers that cold read with edits, which the
       Igor stages again (decision 32).
    4. Whenever the Igor stages, in its own index, which the worker cannot write, every model
       step started so far has exited, it has killed every process the worker user owns, and the
       link checks have passed (decision 32).
    5. The Igor runs prose's second call with the token from step 2, and bug-hunter's minting
       script, against the last staged tree, with `GIT_DIR`, `GIT_WORK_TREE` and `GIT_INDEX_FILE`
       naming its own git directory, the tree and its own index.

    Each trailer that binds a tree, `Prose:` and #153's `Bug-hunter-Tree:`, then names the tree
    the Igor records and publishes (decision 17). It never names the worker's index copy or any
    other copy the worker could change. prose keeps its tokens in the git directory, which the
    worker cannot write, so the worker cannot forge one. The signing scripts come from the
    root-owned `skills_dir` (decision 11), and the three variables keep their git calls in the
    Igor's own git directory, so running them runs nothing the worker wrote. In #153's
    measurement 0.12, run without those variables from inside the tree, they ran a hook and an
    `fsmonitor` command the worker had planted, as the service user.
    *Rejected:* the worker running prose's first call, which cannot write prose's token store
    in the git directory, and could forge a token if that store were made writable to it
    (#153's measurement 0.9); a staging before the kill and the link checks, which would run
    `git add` over the worker's files before the checks see them; and the steps signing for themselves, which
    they cannot do as a user that cannot write the Igor's index.
13. **A changed submodule pointer is published as a pointer once #137 lands** (Adam,
    2026-10-17). A changed gitlink, mode `160000`, is published as the commit it names, the way
    #137 publishes one, and the Igor never enters the submodule. Until #137 lands it stops the
    run, as a link does. A nested repository with working content in it still stops the run.
14. **The worker user's home lasts across runs, and only `~/.claude` and `~/.claude.json` are
    reset before each `claude -p`, from a template built into Igor, keeping nothing of what was
    there** (Adam, 2026-10-17; amended 2026-10-18 by decision 21, which removed the kept stored
    login, `~/.claude/.credentials.json`). #174
    (`pinned-skills`) owns three rules this change relies on: the reset (#174's decision 9); the
    kill of every process the worker user owns before every reset (#174's decision 13); and
    the rewording of the in-force scenario *No state carries between tasks* to name what the
    home keeps (#174's decision 15). Since only `~/.claude` and `~/.claude.json` are reset, `~/.gitconfig` with its `safe.directory` setting and tool caches
    stay, and a file one run leaves elsewhere in the home, such as `~/.npmrc`,
    reaches later runs of the same instance only.
15. **No prose or bug-hunter script runs as the worker user, `prose start` included** (Adam,
    2026-10-18). Adam decided, as #153's decision 16, that the Igor runs prose's first call
    itself (decision 12).
    `prose start` is not that first call: it prints prose's rules for a session and marks the
    session as having read them, while the first call prints the rules and a pass token for one
    commit or post. Adam had decided on 2026-10-17 that `prose start` ran as the worker user after #174's reset, so that
    the session mark it writes sat in the worker's home; the 2026-10-18 decision replaces that.
    The prose pass gets the rules and the pass token in its prompt, so it runs no prose script,
    and no hook in a worker reads a session mark, since #174's plugin installs none. Whether the
    Igor runs `prose start` at all is #153's to say.
16. **Hard links are refused twice** (Adam, 2026-10-17). At startup, the Igor checks that
    `fs.protected_hardlinks` is `1` and refuses to start otherwise; with it, the worker cannot
    make a hard link to a file it cannot read, such as the App's key. And the Igor refuses to
    publish any changed file whose link count is above 1, so a hard link that exists anyway
    stops the run. A hard link to the key is a regular file inside the tree, not a symbolic link,
    so the Igor's symbolic-link checks (decision 9; design, *The Igor reads changes without
    following links*) do not catch one.

17. **The Igor publishes the tree it recorded before #189's checks** (Adam, 2026-10-17). The
    Igor records the tree the model steps left, as a tree object in its own git directory, which
    the worker user cannot write. Then #189 (`loop-verifies-commands`) runs the worked
    repository's checks, the commands such as its tests that the `repos` map in `roles/org.yaml`
    declares for that repository, as the worker user. The Igor publishes the recorded tree. That
    is how it meets #189's rule that what a check writes is not published; the rule, and the
    second worker run when a check fails, are #189's. #189's second worker run is a new run of the
    model steps, and its tree is recorded, checked and published the same way.
18. **Every file the Igor reads from the worker's tree or outbox is opened without following a
    link, and read only if it is a regular file with one hard link** (Adam, 2026-10-17). That
    includes the declaration file, `reverts.json` in the outbox, where the worker states what
    its change discards. An error parsing a file read from the worker never quotes the file's
    content, so a declaration hard-linked to a key cannot carry the key's text into a refusal or
    a record.
19. **Worker trees live in the shared state directory, `/var/lib/igor/trees`, not in the
    instance's private `/tmp`** (Adam, 2026-10-17). #179 (`concurrent-instances`) needs a sibling
    rank to sweep the trees of a rank the roster no longer declares, once that rank is gone, which
    it cannot do in another unit's private `/tmp`. The sibling removes them as the gone rank's
    worker user, through `sudo -n -u igor-worker-<role>-<k>`, where `<k>` is the gone rank (Adam,
    2026-10-18). Every instance runs as the one service user, and the deployment guide keeps a
    retired rank's sudoers line (task 8.4), so the line written for the gone rank lets the
    sibling do this. The unit keeps `PrivateTmp=true` for everything else. The worker-group permissions
    apply under `/var/lib/igor/trees` as they did in `/tmp`: the tree `2770`, the outbox `2770`,
    and `<tree>-git` read-only to the worker. #179's task 1.8 puts trees in the same directory.
20. **The implementation of this change adds the worker users and `sudo` to #192's container
    image** (Adam, 2026-10-17). #192 (`deploy-image`) merges as it is. This change's tasks,
    built at gate two, after this specification is approved, then add, to the
    image and the compose file: `sudo`, a worker user for each instance the compose file runs,
    their sudoers lines, and the trees volume at `/var/lib/igor/trees`. That image is how a Mac
    runs `serve` (decision 3).

21. **Every seat has a Claude token, and Igor never uses a stored Claude login, under `serve`
    or `run`** (Adam, 2026-10-18). Every `claude -p` the Igor starts authenticates with the token
    of the seat it spends, from its environment: the worker and every later model step as the
    worker user, and triage as the Igor. Triage spends the token of the seat the
    budget gate chose (#171's *Triage's model call is made only where a seat can pay for it*).
    Neither the service user nor any worker user is logged in to Claude, and #174's reset deletes
    a login stored in the worker's home. A seat with no token would run on whatever login the
    calling user holds: the service user's for triage, the worker user's for
    the worker, so it could be read under one login and spent under another. #171 refuses a seat
    file that names no token, so no seat runs on a login. That includes #174's startup skills
    check, which spends a seat through the budget gate like any other call (Adam, 2026-10-18).
    The only call whose seat the gate does not choose is #143's seat probe, since task 1.10
    removes the usage read; it authenticates with the token of the seat it reads, and with no stored login. How a person creates a
    token is in
    #171's guides (its task 9.5). *Rejected:* keeping `~/.claude/.credentials.json` so an
    organization with no seats runs on a stored login; such an organization adds one seat from
    its own token instead.
22. **A prompt reaches `claude -p` on stdin, never in its arguments, and the unit sets
    `ProtectProc=invisible`** (Adam, 2026-10-18). On Linux any user can read any process's
    `/proc/<pid>/cmdline`, and a prompt holds the item's text and the lore its scope allows,
    which can be private source content. So a worker of one instance could read the prompts of
    another instance's worker, or of an Igor's triage. Every `claude -p` the Igor starts takes
    its prompt on stdin. Its system prompt cannot share stdin, so it reaches `claude` through a
    file named by `--system-prompt-file`, which the Igor writes where no worker user can write it
    and removes when the process exits. For a process running as the worker user, that is a
    directory the Igor owns beside the tree, `<tree>-prompt`, mode `2750` with the worker's group, never the tree
    or the outbox, which the worker writes; when the Igor starts again after a crash, it removes
    any such file the crash left. Measurement 6.9 confirmed both work with `-p` and
    stream-json output on Claude Code 2.1.303. `ProtectProc=invisible` hides every other user's
    processes inside the unit, so a worker user cannot see the Igor's processes or another
    worker user's. It hides nothing between processes of one user, which is why decision 7
    still gives each instance its own worker user. It needs per-mount `hidepid` support (Linux
    5.8). Measurement 6.8 confirmed it on Linux 6.12, the kernel of Docker Desktop's virtual
    machine; task 6.11 repeats it on the kernel of a Linux server. #192's container has no
    systemd unit, so the setting does not apply there; with prompts on stdin, no argument list
    in the container holds a prompt for another process to read.
    *Rejected:* `ProtectProc=invisible` alone, which leaves the prompt in `ps` output on a host
    whose kernel lacks the feature, and in `sudo`'s log.
23. **A refused start exits with status 78, and the unit stops restarting on it** (Adam,
    2026-10-18). Each of `serve`'s start-check refusals, the missing worker user
    and `fs.protected_hardlinks` among them, exits 78, as #82's (`stopped-scope-visible`) *A
    process that refuses to start exits with status 78* requires. The unit sets
    `Restart=on-failure` and lists 78, and only 78, in `RestartPreventExitStatus=`, as #82
    requires. systemd then shows a refused instance as failed, with Igor's reason in the
    journal, and leaves an instance that exits 0, such as a rank #179 removed from the roster,
    inactive. The number is defined in #82, not here. *Rejected:* a status 79 for a retired
    rank, with `SuccessExitStatus=79`; `Restart=on-failure` never restarts a clean exit. The unit
    also sets `RestartSec=30s`, which Adam decided on 2026-10-19 for #82's unit lines, and this
    change carries them. A start that exits 1, one GitHub or the model provider did not answer
    or one where GitHub refused the App's credential, is then retried every 30 seconds. That
    stays under systemd's default start-rate limit of five starts in ten seconds, which, once
    reached, would leave the instance failed and no longer restarted.
24. **`igor run` spends the token in its own environment, `IGOR_RUN_TOKEN`, as an implicit local
    seat** (Adam, 2026-10-18). Triage and the worker under `run` both authenticate
    with it. Nothing goes in the lore repository and no seat file is needed; `run` never
    decrypts or spends a lent seat. #171 states the rule, in *`igor run` spends its own token as
    an implicit local seat*. This change passes the token to the worker as it passes any seat's:
    the worker's environment holds that token and no other credential. Triage under `run` runs
    in the developer's own home, beside their own Claude login, and still spends the token:
    #174's measurement 0.3 found that a valid token in the environment wins over a stored login,
    and that an invalid one fails rather than falling back to the login.
25. **`igor run` sweeps only rank-0 trees of its own role** (Adam, 2026-10-18; which of them,
    decision 39). Under #179 `run` is rank 0, outside the roster, so its trees are named
    `<role>-0-<id>`. It removes them as the Igor's own user and with no `sudo`, since its worker
    runs as that user. It never removes a tree a `serve` instance left. No worker user
    `igor-worker-<role>-0` is needed, because no other user ever acts on a rank-0 tree: under
    #179 a serving rank never removes one.
26. **Decision 21 needs no seat mechanism of #171's** (checked 2026-10-18). Seats that name
    their token in an environment variable, a file or a command are already on `main`: the
    in-force `seat-budget` requirement *A seat names its token through exactly one mechanism*,
    and `parseOrgBudget` in `src/budget.ts`, which reads `token_env`, `token_file` and
    `token_command`. So every seat can have a token without #171. The build still waits for
    #171's seat code, for decision 45's sake (decision 46). The in-force `seat-budget` still lets
    a seat name no token and an organization with no seats run on the ambient login; #171
    removes both, and archives after this change, in the order issue
    [#204](https://github.com/adamstallard/igor/issues/204) holds for every open change
    (decision 34).

27. **A kill reaches every process the worker user owns, never only a process group** (Adam,
    2026-10-17, as #174's decision 13, for the kill before every reset of the worker's home;
    extended to every other kill from measurement 6.2, proposed 2026-10-18 and approved by Adam,
    2026-10-19). Claude Code 2.1.303 starts
    each Bash command in a new session, so a running `npm test` sits outside both the worker's
    process group and `sudo`'s. In measurement 6.2 a kill of the group ended `claude` and left
    the test running and holding the tree; a kill of every process the worker user owns left
    nothing. So the Igor, as the worker user, kills every process that user owns: on a kill,
    before every reset, before every read or staging of the tree, after #189's checks, and
    before a release. Each instance has its own worker user and runs one
    worker at a time, so that kill reaches no other instance's processes. *Rejected:* the kill
    of `sudo`'s process group, which this change first specified and which misses every command
    the worker runs. Under `igor run` the worker runs as the Igor's own user, where a kill by
    user would kill the Igor and the person's own processes, so a command the worker started
    can outlive a `run` (design, *Risks*).
28. **`deploy/sudoers.example` sets `Defaults:igor !log_allowed`** (proposed 2026-10-18,
    from measurement 6.5; approved by Adam, 2026-10-19). The start check refuses a host without
    it (decision 38). sudo logs every variable passed with `--preserve-env`, value included, so
    without that line the seat token went into the journal on every worker start, where root,
    the `adm` and `systemd-journal` groups and the service user itself can read it. With it,
    sudo logs no command it allows the service user (measurement 6.5); that it still logs one
    it refuses is sudo's documented behaviour, not yet measured (task 6.12). The prompt
    on stdin keeps prompt text out of the log either way (decision 22). *Rejected:*
    `Defaults:igor !syslog`, which also stopped the line but turns off every sudo log line for
    the service user, refusals included.
29. **The git directory sits beside the tree, `<tree>-git`, read-only to the worker, and the
    worker's `git rm` and `git mv` write an index copy in the outbox** (proposed 2026-10-17;
    approved by Adam, 2026-10-19). The worker can write the tree's top directory, so a `.git` inside
    it could be replaced. The Igor reads changes against its own index, never the copy.
    *Rejected:* a sticky bit on the tree's top directory, which would also stop `git rm` of a
    top-level file the Igor owns.
30. **The start check sets `safe.directory=*` in the worker user's own `~/.gitconfig`**
    (proposed 2026-10-17; approved by Adam, 2026-10-19). git refuses a repository another user
    owns, the tree is the Igor's, and the setting is honoured only outside the repository. The
    file affects only the worker user, whose trees are the only repositories it works in.
    *Rejected:* `GIT_CONFIG_*` in the worker's environment, which #156 forbids.

31. **A failed `sudo` spawn of the worker is recorded under a cure key scoped to the whole Igor**
    (proposed in task 0.3; approved by Adam, 2026-10-19). A cure key is #101's key a recurring
    failure is recorded under. One scoped to the whole Igor stops it taking new items, where one
    scoped to an item would fail every item in turn. The Igor does not exit on it (#82).
32. **The Igor may stage more than once, but every staging follows the kill and the checks, and
    both trailers bind the last staging** (Adam, 2026-10-19). Before each staging, every model
    step started so far has exited, the Igor has killed every process the worker user owns, and
    the link and hard-link checks have passed. `Prose:` and `Bug-hunter-Tree:` name the tree of
    the last staging, which is the tree the Igor publishes. Under #153 the Igor stages before
    prose's first call, which lists what the prose pass must rewrite, and again after the
    answers to its cold read; #153 cites this change for the kill and the checks. *Rejected:*
    staging once, after the last model step. That forbade #153's first staging, and it could not
    hold anyway, since the answers to the cold read are model steps that come after it.
33. **The Igor's git calls and the signing scripts run with `GIT_CONFIG_NOSYSTEM=1` and
    `GIT_CONFIG_GLOBAL=/dev/null`, and Git LFS repositories are not supported until a later
    change defines filters the Igor trusts** (Adam, 2026-10-19). A worker's `.gitattributes` can
    name a filter the service user's or the system's configuration defines, such as
    `filter.lfs`, and the Igor's `git add` would run it. With both variables set, the only
    configuration is the Igor's own git directory's, which defines none. The clone and checkout
    run the same way, so an LFS file is checked out and published as its pointer. This
    conflicts with #137's rule that a file stored through a clean filter is published as the
    filter's output; the spec says so.
34. **The in-force ambient login stands until #171 archives** (Adam, 2026-10-19). The in-force
    `seat-budget` lets a seat name no token, and an organization with no seats run on the ambient
    login, until #171 removes both; it archives after this change in #204's order. What is built
    follows decision 21, so the disagreement is in the spec text only.
35. **Citations ahead of #204's order are accepted** (Adam, 2026-10-19). This change archives
    seventh in #204's order, after #120, #137 and #217, whose requirements it cites, but it cites text
    that #174, #171, #179, #82, #208, #153 and #189 add later. #189, #137 and #120 had no place
    in #204's order before; they now have one, so the order says when each requirement this
    change cites comes into force.
36. **The outbox holds the index copy, and the worker's group reads it** (Adam, 2026-10-19). A
    `MODIFIED` block on the in-force *A base change is undone only where the resolution says so*,
    which wanted the outbox empty when the worker starts and writable by the worker alone, lets
    the Igor put the index copy there and lets the worker's group read it. The index
    copy is never read as a declaration.
37. **The start check closes five gaps** (Adam, 2026-10-19). It refuses a path it is given to
    probe that does not exist, since a probe of a missing file passes. It probes each script the
    Igor runs from `skills_dir`, not only the directory's top level, and #174's home template.
    The unit names its environment files to the Igor in `IGOR_ENV_FILES`, so the check probes
    them, `/etc/igor/env` included. A file it has no path for is reported as not checked, never

## Why

A worker can read any file the Igor's service user can read
([#163](https://github.com/adamstallard/igor/issues/163)). Claude Code refuses its own Read tool
and `head` outside the tree, but a test file the worker writes in the tree runs under an allowed
`npm test` and reads whatever it likes. Measured on 2026-10-07, it printed a canary placed outside
the tree. The same route reads the per-role env file, the App's private key (#156), the seat
tokens, the age private key that decrypts seat files once #171 lands, and, on Linux, the Igor's
own `/proc/<pid>/environ`.

A worker takes instructions from issue text, which anyone who can file an issue can write. With
the App's key they can mint installation tokens for every repository the App is installed on,
until the key is rotated. Of the directions in the issue, a separate Unix user is the only one
that doesn't depend on Claude Code enforcing anything.

## What Changes

- **Under `igor serve`, the worker runs as a second Unix user**, `igor-worker-<role>-<rank>`,
  one per Igor instance. The Igor starts it through `sudo`, under a sudoers file with one line
  per worker user, each letting the service user run commands as that worker user. The seat token reaches `claude` through its environment, never its
  arguments, and the prompt through stdin (decision 22). Every later model step in the tree, such as #153's prose pass and bug hunt, runs as
  the same user.
- **The worker gets its tree, its outbox, its seat token and its tools, and nothing else.** The
  tree and outbox are shared through the worker's group, of which the Igor is a member. The
  git directory sits beside the tree, the Igor's and read-only to the worker. `git rm` and
  `git mv` write an index copy kept in the outbox, and the Igor reads the changes against its
  own index, never that copy.
- **Nothing the worker writes is run or followed by the Igor.** The Igor runs git in a tree
  with hooks, fsmonitor and submodule recursion off, and follows no symbolic link. It stops a
  run on a nested repository, a path beneath a link, or a file it cannot read, rather than
  dropping it. A changed link is published as a link once #137 lands, and stops the run until
  then, and a changed file with more than one hard link stops the run. Every file the Igor
  reads from the tree or the outbox, the declaration file included, is read only if it is a
  regular file with one hard link. These checks, and every read and staging of the tree, come
  only once the model steps started so far have exited and their processes are killed. The
  Igor's git calls read no system or global git configuration, so no filter runs (decision 33).
  The Igor makes #153's trailers against the last staging with the signing scripts from
  `skills_dir`, records that tree, runs #189's checks, and publishes the recorded tree.
- **A kill, a release and the startup sweep act as the worker user** where the worker's own
  processes and files need it. A kill reaches every process the worker user owns, since every
  command the worker runs leaves its process group (decision 27). Trees live under the shared
  `/var/lib/igor/trees`, so a sibling
  rank can sweep a retired rank's trees once that rank is gone (#179), as that rank's worker
  user.
- **Every start of `serve` checks the isolation.** `serve` refuses to start, naming what is
  wrong, if the worker user is missing, privileged, or the Igor's own user, if `sudo` asks for a
  password, if the worker cannot run `claude`, or if the worker can read the Igor's process
  environment, a key or token file the Igor's configuration names, an environment file the
  unit names in `IGOR_ENV_FILES`, or a canary, or can write the lore checkout, the Igor's
  installation, #174's home template, `skills_dir` or any script the Igor runs from it. It also
  refuses if a path the check is given does not exist, if sudo logs the commands it allows the
  service user, or if `fs.protected_hardlinks` is not `1` (decisions 37 and 38). A file it has no path for is
  reported as not checked. It refuses if the worker user can reach the cloud metadata
  endpoint, is in a root-equivalent group such as `docker`, can write a container engine's
  socket or holds a sudo right, or if the Igor is still dumpable (decisions 41 to 43). A refused start exits with status 78 (decision 23).
- **A secret reaches the worker only through the Igor, which registers it with #217's
  `rememberSecret`** (decision 41). The Igor passes no agent socket, stores no credential in a
  tree's git directory, and the deployment guide puts none in the worker's home. The unit blocks
  the metadata endpoint and sets `LimitCORE=0`, and the Igor makes itself not dumpable
  (decisions 42 and 43).
- **`serve` always has a worker user, and `run` never does.** `run` runs the worker as the same
  user with a notice.
- **Deployment:** `deploy/igor.service` sets `User=` and `Group=` to the service user and its group, passes
  `%i` to `igor serve`, names the worker user `igor-worker-%i` for the worker's group and
  home, sets `ProtectProc=invisible`, sets `Restart=on-failure` and lists
  78 in `RestartPreventExitStatus=`, and drops `NoNewPrivileges`,
  which blocks `sudo`. A new `deploy/sudoers.example`, which also keeps sudo from logging the
  seat token (decision 28), and a section in `docs/deployment.md` cover creating a worker user,
  its home and its sudoers line for each instance. #192's container image gains `sudo`, the worker users and their sudoers
  lines, and its compose file mounts the trees volume at `/var/lib/igor/trees`. `claude` moves
  out of the service user's home, because the worker must be able to run it.

Not changed: triage still runs `claude` as the Igor. It allows no tools, so the model can run
nothing that would read the Igor's files. It authenticates with a seat's token, never a stored login
(decision 21), and takes its prompt on stdin (decision 22).

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `task-execution`: fourteen requirements added. The worker, and every model step in its tree,
  runs as a separate user. That user can write nothing the Igor depends on, and
  the Igor runs nothing it writes. The Igor reads no file through a link, and publishes the tree
  it recorded before #189's checks. The Igor runs prose's first call, stages only after the kill
  and the checks, and makes #153's trailers itself, against the last staging. A kill and a release reach what the worker owns. The
  isolation is checked before any work. Every `claude -p` takes its prompt on stdin. A secret reaches the worker only through the Igor,
  which registers it, and only the Igor's code and its server decide which secret goes where.
  `gh` and `git` get environments built from a list, and the Igor's memory is never dumped. And `serve` always has a worker
  user, while `run` never does. Four are modified: *The worker is given an explicit environment holding no
  credential but its seat's* also passes `GIT_INDEX_FILE`, naming the worker's index copy, and
  names the surfaces whose credential is kept out; *A kill reaches the worker's whole process
  tree* and *Igor forwards the termination it is sent* kill by worker user under `serve`; and
  *A base change is undone only where the resolution says so* lets the outbox hold the index
  copy, readable by the worker's group (decision 36).

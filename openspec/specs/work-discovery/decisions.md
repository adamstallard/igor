# work-discovery: constraints, rejected alternatives and rationale

## Rationale
- **Rationale: Watermarks reduce reconsideration without governing it.**
  The watermark only spares discovery from examining items again; it must never decide that an item goes unworked. Discovery offers only items updated after the mark, so an item the mark has passed returns only when something updates it. A cycle is one pass in which an Igor, one running instance of Igor, finds items and works them, and a run is one item's attempt within it. `work-claiming` ends a cycle early after two runs in a row that the tracker or code host, which it calls the surface, did not answer (*Two runs in a row that the surface failed stop a cycle*), or after two runs in a row that failed identically before the worker, the subprocess that does the item's work, started (*Two identical failures before the worker on different items end the cycle*). The items the cycle had not reached are unchanged, so the cycle keeps the mark below the oldest update time among them: if the mark passed them, they would never return. A claim refused because the GitHub App the Igor acts as lacks a permission is the same case, so the cycle keeps the mark below that item too: such a refusal is a fault in the Igor's own setup, not in the item (`work-claiming`'s *A fault in the Igor's own setup is not the item's failure*), so the item stays unchanged, and if the mark passed it, it would not return once someone grants the permission. The cost, accepted because the alternative loses the item for good, is that until the permission is granted discovery triages the items updated after the refused item again each cycle.
  Evidence: a cooling-down item fell behind the watermark and never returned, #17
